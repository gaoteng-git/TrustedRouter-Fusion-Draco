# DRACO 评测实战认知收获（TrustedRouter 没说或没说明白的部分）

日期：2026-10-15
背景：在 0G router 上复现/对比 TrustedRouter 的 fusion 架构（3-panel / 5-panel vs
gpt-5.6-sol baseline，DRACO 100 题），历时数日、多次踩坑修复后的认知沉淀。
按重要程度从高到低排列。

---

## 1. Fusion 的"领先优势"里混着 prompt 调优的水分（最重要）

TrustedRouter 博客只报 Prometheus 2.0 77.4 vs GPT-5.5 solo 63.3，从不披露融合侧的
写作指令被调优到什么程度、baseline 是否得到同等对待。我们复现时犯了同样的错（只给
fuser 的 FINAL_INSTRUCTION 加了"保留细节/引用内联/预算兜底"三段调优），随后用
parity 实验（branch `baseline-prompt-parity`）直接量化：仅把等价写作指令补给
baseline 的 SYNTHESIS_INSTRUCTION，baseline 即涨 1.2-1.9 分（全量结果待跑完）。
**"融合架构本身的贡献"可能只有表面分差的一半到七成。**

> 读任何 fusion 对比 benchmark 前先问：两边的 prompt 功夫下得一样吗？

## 2. Fusion 的优势是领域依赖的——金融深研题上基本消失

非财务 80 题：3-panel 领先 baseline 约 2.5 分（胜率 61%）。
金融 20 题：65.47 vs 64.99，打平（胜率仅 8/20）。
根因：金融题得分卡在"能否挖到财报脚注里的冷门精确数字"（认股权证行权价、定期贷款
利率、分红总额等），这是单模型研究深度的比拼，多视角融合帮不上忙。失分大头甚至不在
XBRL 结构化数据里（sec_facts 工具查不到），必须读 10-Q/8-K 原文脚注。
博客给了分类分数（Law 93.3 等）但从未划出"此架构在哪类任务上无优势"的边界。

## 3. Fusion 上限被面板的"检索召回率"锁死

对 22+3 道输题逐题归因：约一半失分案例里，**所有面板成员都没查到关键事实**——
fuser 的输入里压根没有，写作指令调得再好也无济于事。
fusion 的本质是**面板召回率的放大器，不是无中生有的增强器**。
这也解释了 5-panel 为何强于 3-panel：多两个独立搜索者 = 多两次撞对冷门信息的机会。

## 4. 成本结构真相：fusion 可以又好又便宜，前提是面板选对

- 3-panel 总成本 = baseline 的 **0.55x**（且高 2 分）：gpt-5.6-sol 输出单价
  （$30/M）是便宜面板模型的 20-60 倍。
- 5-panel 贵至 2.7x：**68% 成本来自两个贵价成员**（kimi-k3 $42 + qwen3.8-max $38，
  65 题口径）。
- fuser 角色会放大模型单价差：同样工作量，minimax-m3 当 fuser $0.82，
  kimi-k3 当 fuser $10.28（12.5x）——因为 fuser 是输出长文的角色。
- 成本大头完全相反：fusion 的大头是搜索（N 面板独立搜），baseline 的大头是 LLM。
- 定价反直觉案例：mimo-v2.5-pro 名字带 "pro" 但单价是全面板最便宜档之一。

博客只说 "fraction of the frontier panel's cost"；这套可操作的拆解是自己算的。

## 5. Fuser 有固定且可复现的失败模式

1. **主动过度压缩**：把手头最好的面板答案压掉 40-90%、删光内联引用——
   哪怕 token 预算明明够用（finish_reason=stop）。
2. **用"来源有分歧"逃避裁决**：把 panel 冲突写成悬而未决的旁白而非裁出明确数字，
   恰好撞上 rubric 的精确数字评分点。
3. **弱来源放大**：比单模型更易把论坛帖当权威引用、把有利框架说过头，
   踩中负权重 anti-pattern 扣分项。
4. 即使有明确指令（"不要省略任何数字"），个别情况下仍会丢
   （实例：a78eed67 的 $250M/SOFR+1.20% 定期贷款条款，deepseek 面板答案里有、
   融合输出里没有）。指令能缓解、不能根治。

## 6. 打分协议本身是承重墙，而且很脆

- criterion chunk size=3 是防分数虚高的（批量判分宽松 +7~15 分；answer-first
  顺序再虚高 +4-5 分）——换一套打分参数，排行榜数字就变。
- 判官无参考答案、纯靠自身知识核实——冷门事实上判官自己也可能错。
- 实测存在"事实在答案里、判官仍判 not met"的措辞过严案例
  （写 "73%" 不算、须 "73.09%"）。
- 近似平局的题，判官多次打分间的随机波动足以翻转胜负。
- 判官 rationale 字段存的是空串，事后归因必须自己去答案文本里找证据。

## 7. 新网关跑评测的真拦路虎：兼容性矩阵，不是模型能力

0G router 实测踩坑清单（每个都是"模型没问题、参数组合/传输层有问题"）：

| 坑 | 现象 | 修复 |
|---|---|---|
| 官方 SDK 全军覆没 | 0G 流式响应缺 `data: [DONE]` 哨兵，SDK 全部判失败 | 绕过 SDK，直连非流式 HTTP |
| minimax-m3 | 硬拒 `response_format: json_object` | 按模型条件跳过该参数 |
| gemini-3.1-pro | `response_format`+`reasoning_effort` 组合 503 | 同上（曾致整条流水线两次 FATAL） |
| kimi-k3 | 硬拒 `temperature` | 按模型跳过 |
| 某 provider | 幽灵 `metadata` 400（我们从未发过该参数） | 重试换 provider 自愈 |
| **长连接静默掐断** | 空闲 keep-alive 被服务端关闭 → SSL EOF；手动 curl 永远复现不了（每次新连接） | 重试逻辑必须覆盖 ConnectError，不能只盖超时/5xx |

## 8. 长跑评测的工程卫生学

- **resume 语义逐处核对**：面板覆盖判定 `any()` vs `all()` 差一个词，20 道题带着
  残缺面板"抢跑"融合，污染全部对比数据（后清理重跑）。
- **"ok-但-空内容"死循环**：生成侧 status=ok（resume 不重跑）+ 内容为空（打分侧
  永远失败）→ 每轮徒劳重试。生成侧应把空内容判为 failed。
- **进度监控不能信日志**：Python 输出全缓冲使日志滞后真实进度几十分钟到数小时,
  以数据文件行数和 mtime 为准。
- **数据溯源提前设计**：jsonl 未存每行 prompt 版本 / 判官真实 usage / Exa 真实
  cost_dollars，每一样都让事后分析多费一倍功夫。

---

## 一句话总结

TrustedRouter 的技术叙事基本是实的，但"fusion 赢多少"这个数字的构成远比博客呈现的
复杂——**prompt 调优对称性、任务领域、面板选型**三个变量，每一个都足以让结论翻面；
我们现在手里有能把这三个变量拆开算账的第一手数据。
